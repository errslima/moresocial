## 2. Architecture map

| Area | Files | Notes |
| --- | --- | --- |
| Config and secrets | `app/config.py`, `app/security.py` | Env vars plus secret files. Synthetic providers and the fake AI are refused in production and on `https://1f517.com`. Credentials are encrypted with Fernet using a key file kept outside the database. |
| Schema | `app/models.py`, `migrations/versions/0001_initial_schema.py` | Every owned row has `workspace_id`; links between owned rows use composite `(workspace_id, id)` foreign keys. The migration was autogenerated and then checked with `alembic check`. |
| Tenancy | `app/repo.py` (`Scoped`) | Handlers go through `ctx.ws`. There is no lint rule enforcing this; it relies on review. |
| Web | `app/web.py`, `app/pages.py`, `app/auth_routes.py`, `app/templates/`, `app/static/` | Server-rendered Jinja with `StrictUndefined`. Origin check on all non-GET requests plus a session CSRF token. Strict CSP. `/internal/*` returns 404 on the public app. |
| Internal API | `app/internal.py`, `app/serve.py` | Port 8001, separate from the public 8000. Two roles: a per-workspace connector key, and the operator key for the provisioner. |
| Google | `app/google.py`, `app/google_sync.py`, `app/accounts.py` | One code path for real and synthetic providers; only the transport, authorize URL and ID-token verifier are swapped. |
| Ingestion | `app/ingest.py` | Idempotent upserts, identity by exact provider identifier, exclusion tombstones, and `invalidate()` for derived data. |
| Memory and AI | `app/memory.py`, `app/retrieval.py`, `app/ai.py`, `app/fake_generation.py` | Chunking, extraction, hybrid search, cited answers and budgets. |
| Gatherings | `app/gatherings.py` | Drafts, rewrites, RSVP suggestions, calendar conflicts, next steps. |
| WhatsApp | `app/whatsapp.py`, `connector/`, `deploy/provisioner.py` | The connector is adapted from EnzoSocial with its send, photo and repair paths removed. The provisioner runs on the host. |
| Jobs | `app/jobs.py`, `worker/main.py` | A Postgres queue with `SKIP LOCKED`, leases, idempotency keys and `defer` for budget pauses. |
| Synthetic | `app/synthetic.py`, `app/synthetic_data.py`, `app/dev_routes.py` | HMAC-signed stateless codes and tokens, so separate web and worker processes agree. |
| Deploy | `deploy/*`, `scripts/*`, `.github/workflows/ci.yml` | Covered in the operator runbook. |

## 3. Known deviations and weak spots (please judge these)

Ranked by how much I would want a reviewer to look.

1. **The real AI adapters are untested.** `AnthropicVoyageProvider` in `app/ai.py` has no tests,
   not even with a mocked SDK response or a mocked Voyage transport. Every AI test uses
   `FakeProvider`. Please check these points before relying on it:
   - SDK usage: `beta.messages.create(..., fallbacks='default', betas=[...])` and
     `output_config` combining `effort` with `format`.
   - Usage-field handling.
   - The Voyage request and response shape.

   A small mocked test for both would be cheap.
2. **Two GET requests write to the database**, although the plan says there should be no
   state-changing GET except the OAuth callback. `GET /api/whatsapp/status.json`
   (`whatsapp.status`) records the observed connector state and the account ID. In synthetic
   mode it even ingests the fixture packets. The writes only mirror remote state, but they
   break the rule as written. Options: a POST poll, or a provisioner or worker loop that
   records status.
3. **Gmail incremental sync can silently drop messages.** `_gmail_incremental` caps new message
   IDs at `gmail_max_messages` (500) but still advances the cursor. A burst above 500 between
   polls would lose the extra messages without marking the stream truncated. It should either
   set `truncated`, or process in batches before moving the cursor.
4. **Asking and drafting run synchronously inside the web request.** Each request can take up to
   90 seconds with two SDK retries, and each ask holds the request's DB session while also
   opening short sessions for budget reservation. The pool is 5 + 5 overflow. That is fine for a
   two-user beta and a problem if concurrency grows.
5. **Scope removal can be rolled back.** `google_sync._load` sets a stream to `disabled` when a
   scope is missing and then raises inside the same session, so the change rolls back. It is
   harmless today because `store_grant` already disables those streams, but it is misleading.
6. **Rate limiting is in memory.** `auth_routes.throttle` keeps its counts per process and loses
   them on restart. The client IP relies on the fixed Compose gateway `172.31.77.1` in
   `TRUSTED_PROXY_IPS`. If that subnet changes without updating the setting, every user shares
   one bucket (20 sign-in starts per 10 minutes, globally).
7. **Unlinking an identity is a heuristic.** `ingest.unlink_identifier` moves claims whose
   evidence was *authored* by that identifier. Claims about that person that come from other
   people's messages stay with the original profile.
8. **Two token refreshes can race.** The web and worker processes can refresh the same Google
   token at once; there is no lock. The last write wins. It is probably harmless, but it is
   unverified against Google's behaviour.
9. **The connector has never run against WhatsApp.** `connector/index.js` has only been
   syntax-checked and import-checked with `whatsapp-web.js` 1.34.7. The Node tests cover the
   extracted pure modules (`server.js`, `history.js`, `queue.js`, normalization), not the client
   wiring. The plan's live QR smoke test is still required.
10. **The provisioner assumes names.** It expects the web container to be named
    `moresocial-web-1` (Compose project `moresocial`) and runs `docker` as root through
    systemd. Orphan cleanup waits for three consecutive checks (about 30 seconds) and is skipped
    when the API is down or reports zero workspaces. Please review that safety logic in
    `Provisioner.reconcile`.

## 4. Other deliberate changes

- EnzoSocial's `patch-library.cjs` is not used; it only patched the send path.
- Static files are served by a whitelisted route. `StaticFiles` resolves paths wrongly when
  `root_path` is set and the proxy has already stripped the prefix.
- Calendar events first seen as already cancelled are never stored.
- Account deletion deletes the workspace row, and the cascade removes all owned data. Connector
  containers and session directories are then removed by the provisioner's orphan cleanup, not
  by the web app.
- Confirmed claims survive deletion of their evidence and switch to `basis='user'`. Unconfirmed
  extracted claims without remaining evidence are deleted.
- A cached answer whose evidence is deleted has its text replaced and is marked stale. A draft is
  only marked stale and keeps its text, because the user may have edited it.
- Secret files in production are `0444` inside a `root`-only `0700` directory, because Compose
  file secrets are bind mounts and the containers run as different users.

## 5. Suggested review checklist

- [ ] Tenancy: search `app/pages.py`, `app/gatherings.py` and `app/retrieval.py` for any query
      that does not go through `ws.q(...)`, `ws.get(...)` or an explicit `workspace_id` filter.
      The raw SQL in `retrieval.search_chunks` and `retrieval.evidence_for` filters by `:w`.
- [ ] OAuth callback (`auth_routes.google_callback`): single-use flow consumed in its own
      transaction, then browser binding, code exchange, identity checks, allowlist, grant storage
      and a new session, in that order.
- [ ] The deletion race in `memory._still_valid` and `memory.extract_chunk`: sources are locked
      `FOR UPDATE` before publishing.
- [ ] `ingest.invalidate` covers chunks, embeddings, claims, answers, drafts and RSVP suggestions.
- [ ] Budget reservation and reconciliation (`ai.reserve`, `ai.reconcile`): a failure with unknown
      cost keeps the reservation.
- [ ] Compose and Dockerfile: no secrets in the build context (`.dockerignore`), only loopback
      ports, read-only filesystems, dropped capabilities.
- [ ] `deploy/release.sh`: builds from `git archive` (tracked files only), migrates once, and
      switches the symlink only after `/ready` succeeds.
- [ ] Items 1–3 in section 3.
